# CLAUDE.md — правила разработки

## Проект
Smart AI Travel Planner: LLM выбирает локации из БД, алгоритм (TSP / PostGIS) строит кратчайший пеший маршрут.
Стек: Python (FastAPI), PostgreSQL + PostGIS, Next.js + Leaflet. Дорожная карта — в `PROJECT_PLAN.md`.

## Структура (целевая)
- `backend/` — FastAPI, миграции Alembic, тесты pytest
- `frontend/` — Next.js
- `docs/` — заметки и бенчмарки

## Коммиты: Conventional Commits
Формат: `<type>(<scope>): <описание>` — в повелительном наклонении, до ~72 символов, без точки в конце.

Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
Scope (опционально): `backend`, `frontend`, `db`, `llm`, `optimizer`, `infra`.

Примеры:
- `feat(optimizer): add 2-opt improvement for TSP route`
- `fix(db): add missing GIST index on places.geom`
- `chore: initial repository setup`

Breaking change: `!` после типа/scope и пояснение в теле коммита.

## Правило атомарных коммитов
- Один коммит = одно логическое изменение.
- Не смешивать фичу, рефакторинг и форматирование в одном коммите.
- Тесты и код, который они проверяют, — в одном коммите.
- Каждый коммит должен оставлять проект в рабочем состоянии (сборка и тесты проходят).
- Добавлять файлы явно (`git add <файлы>`), не `git add -A` вслепую. Перед коммитом смотреть `git status` и `git diff --staged`.

## Секреты и .env — строгий запрет
- **Никогда** не коммитить и не пушить `.env` и любые файлы с ключами/токенами/паролями (`GEMINI_API_KEY`, `OPENAI_API_KEY`, пароли БД и т.д.).
- В репозитории хранится только `.env.example` с пустыми/фиктивными значениями.
- Ключи не хардкодить в коде, тестах, логах и документации.
- Если секрет случайно попал в коммит — считать его скомпрометированным, перевыпустить ключ, затем чистить историю.

## Что не коммитить
`.env`, `venv/`, `.venv/`, `node_modules/`, `.claude/`, кэши и артефакты сборки (см. `.gitignore`).

## Правила кода
- Python: типы обязательны, форматирование и линт через ruff, проверка типов mypy.
- TypeScript: strict-режим, eslint + prettier.
- LLM возвращает только структурированный JSON, который валидируется (Pydantic). Выбор локаций — по `id` из списка кандидатов; координаты и порядок обхода LLM не определяет.
- Гео-запросы — через PostGIS (`geography`, `ST_DWithin`), с GIST-индексами.
- Новая логика сопровождается тестами; внешние API (LLM) в тестах мокаются.

## Рабочий процесс
- Для нетривиальных изменений — сначала короткий план, затем реализация малыми шагами по `PROJECT_PLAN.md`.
- После завершения шага отмечать пункт в `PROJECT_PLAN.md`.
- Основная ветка — `main`; фичи — в ветках `feat/...`, `fix/...`.
